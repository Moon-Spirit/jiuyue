# 不把 123 云盘接入为存储后端

Status: accepted（否决提案）

曾计划把 123 云盘作为 `Storage` 的可选实现，以降低服务器磁盘占用。经调研（全文见 [`docs/research/123pan-storage-backend.md`](../research/123pan-storage-backend.md)）**否决该方案**。三条独立阻断，任一条即足以否决。

## 阻断一：条款与商业模式冲突（致命）

开放平台协议设定的服务模型是**「开发者的用户登录自己的 123 云盘账号」**，而不是「应用自己持有一个账号，把所有用户的数据存进去」。协议原文：

> 开发者可将123云盘相关功能嵌入到自有的应用程序或硬件端，**开发者的用户可登录123云盘帐号**使用123云盘相关功能

协议同时禁止通过数据接口开展竞争性业务：

> 不得……利用123云盘开放平台提供的数据接口开展与西安一二三云计算有限公司**存在竞争关系的业务**

123 云盘官方公告更直接点名了我们要实现的这个模式：

> 有一类用户并非普通使用者，而是利用平台规则漏洞，进行**批量注册、破解接口、盗链建站，甚至搭建影视网站、小文件下载站等商业服务**

即：把网盘当作应用的文件后端与 CDN，正是他们正在封堵的行为。

## 阻断二：出流量计费摧毁经济性

每一次终端用户下载都计入提取额度：免费档 **10 GB/月（全部客户端合计）**，超出 0.05 元/GB，未登录下载通道已被移除。额度耗尽时 `download_info` 返回错误 `5113`。聊天应用的流量以附件下载为主，**出流量是主要成本项**，这里没有不计量路径。

## 阻断三：限流与聊天负载不兼容

官方文档的免费档 QPS：`api/v1/file/list` = **0.2**（每 5 秒一次请求）、`file/delete` = 1、`file/move` = 3、`api/v2/file/list` = 5；且同一 `client_id` 下**最多 3 个有效 token**。凭证本身也已收费（需先购买开发者权益包）。这与聊天应用的读写频率相差数个数量级。

## 其他事实

- **没有官方 Rust SDK**，**没有 S3 兼容端点**，**没有任何开源项目**把它当作通用应用存储后端。
- 唯一的 Rust crate（`restic-123pan`）用的是**逆向的 Web 接口**（用户名密码登录），不是本文讨论的开放平台 API；这不是可效仿的先例。
- rclone 的 123pan 后端（PR #9047）**被关闭而非合并**，仓库现有后端列表中不存在。

## 决定

- `Storage` trait 保留，但实现清单为：**本地磁盘（默认）** + **S3 兼容对象存储（扩容路径）**。123 云盘**不进入实现清单**。
- 若将来仍需要，第三方网盘接入是一个**有界增量**（trait 已就位），但**不得成为依赖前提**，且必须重新评估条款。
