# 邮箱验证与密码找回：投递是一条 trait 缝，链接是可消费的摘要

Status: accepted

邮箱地址的**验证**与密码的**找回**都依赖同一件东西：一封带到一次性链接的邮件。本 ADR 记录两件事的设计取舍——邮件怎么送（`Mailer` 缝），以及链接怎么算可信（一次性、有时限、只存摘要）。

## 决定

### 1. 邮件投递是一条 `Mailer` trait 缝，不选具体服务商

- `jiuyue-auth` 只依赖 `jiuyue_auth::Mailer` trait（`send(OutgoingMessage) -> Result<(), MailError>`）。谁把邮件真正送出去，是部署决定，不是领域决定。
- 仓库内置的实现是 `InMemoryMailer`：它**不发送任何东西**，只把消息留在内存里并打一条日志。测试从它断言；本地开发者从进程日志里就能读到验证 / 重置链接。
- **生产必须自己提供**：一个 SMTP 或事务邮件 API 的实现，经 `AuthService::builder(...).mailer(...)` 注入（例如基于 `lettre` 或某家 API 的薄封装）。除这一处外，本 crate 没有任何地方知道主机名、端口或 API key。
- 当前构建**没有**内置任何真实投递实现，因此 `SMTP_URL` 一旦被设置，**服务拒绝启动**（`Error::MailTransportUnsupported`），而不是接受注册与重置、却把所有链接只写进日志。这是一个安全失败，不是一个缺失功能。

### 2. 发送永远不阻塞请求路径

- 链接落库（我们自己的数据库，快）之后，消息交给 `tokio::spawn` 出的任务去投递，请求立即返回。慢的服务商无法让注册或重置请求挂起；最坏情况是一条"投递失败"的日志。
- ADR-0010 已经说明：单机 2C2G 上**后台发送进程可以，消息中间件不行**。这里正是那个后台发送者：进程内 spawn，没有 broker、没有队列服务。

### 3. 一次性链接：256 位随机值，只存摘要，原子消费

- 令牌是 256 位 OS 随机数（base64url 无填充，43 字符）。**只存 SHA-256 摘要**（`account_tokens.token_hash`，`^[0-9a-f]{64}$` 约束钉住形状），与 `sessions.refresh_token_hash` 同一纪律：数据库泄露得不到可出示的凭据。
- 兑换是一条原子 UPDATE：`WHERE token_hash = $1 AND purpose = $2 AND consumed_at IS NULL AND expires_at > now() RETURNING user_id`。**先消费，再做后续动作**——标记账号已验证 / 改密码若中途失败，令牌仍保持已消费，因此"一次性"是事实而非建议。
- 时限由**数据库时钟**判定（`now()` 与 `expires_at` 比较），与写行时用的时钟一致：验证链接 24 小时，重置链接 1 小时。
- `purpose`（`email_verification` / `password_reset`）把两类链接分开：验证链接不能当重置链接用，反之亦然。
- 同目的的新链接会**作废该用户此前所有未消费链接**（发新链接 = 旧链接失效）。

### 4. 失败可区分，但有两处刻意不区分

- 可区分：链接过期 → `TOKEN_EXPIRED`（HTTP 410）；链接未知 / 已用过 / 不完整 → `TOKEN_INVALID`（HTTP 400）；账号未验证而动作受限 → `EMAIL_NOT_VERIFIED`（HTTP 403）。客户端因此能给出"重新申请一封"这类可操作提示，而不是笼统失败。
- 刻意不区分："已用过"与"从未存在"都答 `TOKEN_INVALID`——两者对用户是同一个动作（重新申请）。令牌是随机值，区分二者对攻击者没有价值，对用户也没有帮助。

### 5. 找回密码不是账号探测仪

- `POST /auth/forgot-password`、`POST /auth/resend-verification` 对**存在与不存在**的地址返回**逐字节相同**的 `202 {"accepted": true}`。
- 两者做的工作也相同：`find_user_by_email` 照常执行，链接写入走 `INSERT … SELECT … WHERE EXISTS (users)`——账号不存在时写 0 行，但执行的是同样的语句，因此耗时特征一致。请求路径上唯一的差别是"是否 spawn 一次投递"，而投递不在请求路径上。
- 限流键是**来源**（`X-Forwarded-For` 的最后一个地址，即 Caddy 追加的那个），从不按地址计数，因此被限流的响应同样无法透露地址是否存在。

### 6. 验证是增量，不是追溯；受限动作由服务端强制

- 既有账号（`email_verified_at IS NULL`）**继续可用**：注册后立即可登录、读自己的资料、读写已有会话。验证只是把标记从 false 翻到 true。
- **唯一受限动作：开启新会话**（`POST /conversations/direct`、`POST /conversations/group`）。理由：开启会话是账号第一次主动触达他人，是邮件验证真正要拦的场景（拿一次性邮箱批量骚扰陌生人）。它由 `AuthService::authenticate_verified` 在**服务端**强制，UI 隐藏按钮不是控制手段。
- 前端据此在会话页显示一条"邮箱未验证 → 去验证"的提示条；服务端拒绝时返回 `EMAIL_NOT_VERIFIED`，前端据此给出同样明确的指引。

### 7. 限流复用既有实现，但独立计数

- 触发邮件的端点复用 `LoginAttemptStore` / `LoginAttemptPolicy`（见 `limiter.rs`），不新发明一套限流。
- 但登录与邮件是**两个独立的桶**：一个来源狂刷重置请求，不应该顺带锁死它的登录；反过来也一样。`AuthService::builder` 的 `login_store` / `email_store` 分别注入。
- 每一次被接受的邮件请求消耗一格预算（复用 `record_failure` 的语义：它计的是"消耗预算的尝试"）。窗口内达到阈值后，**下一个**请求被 429 拒绝，与登录限流的行为一致。

## Considered Options

- **链接本身是 JWT（自包含、无状态）** — 否决：JWT 无法被"用掉"。一次性与可撤销要求服务端状态，而"改了密码就作废全部会话"也需要状态。既然如此，状态化的一次性令牌比"JWT + 吊销表"更简单、更诚实。
- **明文存令牌** — 否决：数据库泄露即得到可用的重置凭据。摘要存储的成本只是一次 SHA-256。
- **由本 ADR 选定 SMTP 服务商** — 否决：这是部署方与运维的决定，不是领域模块的决定。代码只保留注入点。
- **同步等待发送完成再返回** — 否决：慢服务商会让注册与重置挂起，违反"发送不得阻塞请求路径"，也把一次第三方故障变成一次注册故障。
- **把未验证账号全面锁死（不能登录 / 不能发消息）** — 否决：与"既有账号继续有效"冲突，且惩罚过重；真正需要防的是"未被验证就触达他人"。
- **为找回密码端点发明第二套限流** — 否决：`limiter.rs` 已经是同一形状问题的解，复制一份只会让两处阈值漂移。

## Consequences

- 生产上线前**必须**先补一个 `Mailer` 实现，否则只能跑开发传输（链接进日志）。这是刻意留下的、写进部署清单的空位；`SMTP_URL` 的启动失败就是提醒。
- 邮件模板与文案集中在 `links.rs`，是将来接 i18n 的唯一入口。
- `account_tokens` 会随邮件量增长；已消费 / 已过期的行可以按运维脚本清理（当前不清理，因为"已用过"需要与"从未存在"在语义上可区分到日志层面，且清理不是本工单的验收项）。
- 重置密码会**吊销该账号全部会话**：改密码意味着"用旧密码打开的设备全部退出"，这是安全属性，不是副作用。
