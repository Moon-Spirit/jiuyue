# 单机起步，按百万级目标设计

Status: accepted

容量目标定为**百万级注册**，但首发部署在单台 2 vCPU / 2 GB 服务器上。这两件事不矛盾，前提是把"按百万级设计"理解为**架构决策不留扩展死角**，而不是"在 2C2G 上跑百万并发"。因此：应用层从第一天无状态；数据模型按可分区设计；扇出策略分级；扩容路径写进文档。

## 为扩容预留的具体决策

- **应用层无状态** — 连接状态、Presence、会话状态全部外置到 Redis；任意节点可服务任意连接；跨节点广播走 Redis pub/sub（单机时逻辑照常运行，加节点只是多进程）。
- **数据模型可分区** — 全局 Message ID 时间可排序；消息按"会话时间线 + 每用户读游标"存储，**不为每个参与者复制消息**（这是百万级扇出的关键）；消息表预留分区键。
- **扇出分级** — 小群写扩散，大群/频道读扩散，模型上分开。
- **存储抽象** — 见 ADR-0006。
- **扩容路线图** — 单机 → 媒体服务独立（见 ADR-0004）→ 应用层水平扩 → 数据库主从/分区、Redis 集群。每一步都不需要改代码逻辑。

## Considered Options

- **直接上分布式**（多节点 + 消息队列 + 分库分表）— 被否决：与现有 2C2G 硬件严重不匹配，提前支付复杂度成本，且违反"为不需要的规模写复杂度"的原则。
- **纯单机写法**（进程内存保存状态、全局自增 ID、直接内存广播）— 被否决：与已确认的百万级目标直接冲突，后期需要重写而非扩容。

## Consequences

- 2C2G 实测容量约为**一两千并发 WebSocket**；百万级是**架构天花板**，不是首发容量。对外表述与容量规划都必须区分这两者。
- Redis 在单机阶段"看起来多余"（进程内广播已够用），但它是无状态化的前提。必须接受这份前期成本。
- 任何"反正现在单机"式的捷径（本地文件写路径、进程内计数器、单例状态）都被本 ADR 禁止。
