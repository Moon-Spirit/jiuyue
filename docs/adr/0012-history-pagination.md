# 历史分页：以会话 seq 为游标向后翻页

Status: accepted

`GET /conversations/{id}/messages` 不再是"最近 N 条"的固定窗口，而是一套**游标分页契约**。游标是会话内 **Sequence Number（seq）**——ADR-0003 定义的会话内排序唯一权威：

- 请求参数 `before`（可选，**排他**）：返回 `seq < before` 的消息；省略即取最新一页。
- 请求参数 `limit`（可选）：页大小，服务端钳制在 `[1, 100]`，缺省 50。
- 响应：`messages` 永远按 `seq` **升序**（由旧到新）；`next_before` 是取更早一页时应回传的 `before`；`has_more` 表示是否还有更早的消息。

翻页方式：不要 `before` 取最新页；再用响应的 `next_before` 取更早的一页。把第 N+1 页拼在第 N 页前面，就能无重复、无缺口地还原整段历史。

契约类型定义在 `backend/crates/contract/src/chat.rs`（`MessagePageQuery`、`MessageList`），TypeScript 由 `scripts/gen-contract.ps1` 生成，前端不手写副本。

## 理由

1. **游标锚定在不会移动的值上。** `LIMIT/OFFSET` 的分页边界是一个会随插入漂移的**计数**：翻到第 2 页之前如果来了新消息，页边界整体后移，客户端就会**重复或跳过**消息。`seq` 是单调分配且写下后不再变化的，`seq < before` 的边界在并发写入下保持稳定。
2. **用得上 `(conversation_id, seq)` 索引。** 该唯一约束的索引前导列正好是查询谓词与排序键，取一页是一次索引范围扫描，既不扫描也不在内存里排序整个会话。
3. **一页一行的大小有上界。** 客户端无法一次请求整个会话，避免在 2 vCPU / 2 GB 的机器上造成内存炸弹。`limit` 只做钳制、不报错，过头的客户端仍能拿到可用的一页。
4. **排序显式且确定。** 响应固定升序，刷新前后顺序一致；分页不会改变"按 seq 排序"这一唯一权威。

## Considered Options

- **`LIMIT/OFFSET` 分页** — 否决：边界随并发插入漂移，会重复/丢失消息，正是本工单要消灭的生产事故。
- **时间戳游标（`created_at < ...`）** — 否决：时间戳不是排序权威（CONTEXT.md），同毫秒并发无法定序，且客户端时钟不可信。
- **继续只返回固定窗口、不分页** — 否决：无法读取更早历史，且窗口大小写死在两端必然漂移。
- **未钳制的 `limit`** — 否决：一个 `limit=100000000` 就能让单机 OOM。

## Consequences

- 前端滚动到列表顶部时请求更早一页，并在**前置**消息后补偿滚动偏移，避免视口跳动（`frontend/src/components/chat/MessageList.vue`）。
- 这一版**只做向后翻页**。向前补洞（断线重连后的缺口修复）属于另一张工单，届时会复用同一 `seq` 权威，而不是新造一套游标。
- 分页只覆盖当前列表渲染，不包含虚拟滚动与搜索（各自独立工单）。
- 查询按 `(conversation_id, seq)` 访问，与 ADR-0005 的"按 `conversation_id` 分区"计划完全兼容：将来改为分区表后，同一查询仍然只命中一个分区、仍用本地索引。
- 分页是**读**路径的契约；写入路径的原子 seq 分配与幂等发送保持不变（见 ADR-0003 与 `jiuyue-chat`）。
