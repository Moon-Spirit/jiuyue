## Problem Statement

想自己掌控聊天数据的人，今天没有合适的选择。

商业 IM（微信、Telegram、Slack）功能完整，但数据在别人手里，无法自托管，也无法审计它到底存了什么。自托管方案里，企业级的（如 Mattermost）部署与运维门槛高、上手重；玩具级的项目功能残缺，不敢真用。而"隐私"与"可用"通常被当成二选一——要么全量端到端加密到搜索、多设备、审核全部失效，要么放弃加密。

结果就是：想搭一个**自己说了算、又能真正日常使用**的聊天工具，找不到既完整又可运维的答案。

## Solution

jiuyue 是一个可自托管的、产品级完整度的即时通讯应用。它同时提供：

- **完整的现代 IM 体验**：单聊、群聊、消息撤回/编辑/引用/表情回应、@提及、已读回执、正在输入、在线状态、多设备同步、离线补发、消息搜索、文件与音视频消息。
- **可用的音视频通话**：1:1 走 P2P WebRTC，群组走 SFU；通话在**独立的窗口**中进行，不占用主窗口。
- **真正的端到端加密**：以"云端会话 + 秘密聊天"双模式同时满足隐私与可用性——云端会话支持搜索、多设备与内容审核；秘密聊天是单设备的真 E2EE，服务端只见密文。
- **可自托管的部署形态**：单机 Docker Compose 即可跑起来，架构按百万级设计，扩容只需加机器。
- **可运营的能力**：举报、敏感词审核、管理后台。

用户拿到的是一个**自己的服务器 + 自己的数据 + 不将就的体验**。

## User Stories

### A. 账号与认证

1. 作为访客，我要用邮箱和密码注册账号，以便开始使用。
2. 作为新用户，我要收到验证邮件并点击链接完成验证，以便确认邮箱真实有效。
3. 作为用户，我要用邮箱和密码登录，以便访问我的会话。
4. 作为用户，我要通过 GitHub 一键登录，以便省去记忆和输入密码。
5. 作为用户，我要通过 Google 一键登录，以便省去记忆和输入密码。
6. 作为用户，我要在忘记密码时通过邮件重置密码，以便重新获得访问权。
7. 作为用户，我要在登录后长期保持登录状态（访问令牌过期后自动续期），以便不必反复登录。
8. 作为用户，我要查看当前登录的所有设备及其位置/时间信息，以便发现异常登录。
9. 作为用户，我要远程注销指定的其他设备，以便在设备丢失时保护账号。
10. 作为用户，我要登出当前设备。
11. 作为用户，我要修改自己的密码。
12. 作为用户，我要注销账号，并了解数据会被如何删除。
13. 作为用户，我要在连续多次登录失败后受到限制，以便我的账号不被暴力破解（也让我看到明确的提示）。
14. 作为用户，我要在注册时设置唯一的用户名（@handle），以便他人能精确找到我。
15. 作为新用户，我要在注册时填写昵称和上传头像，以便别人认得出我。
16. 作为系统，我要拒绝同一邮箱重复注册，并给出明确提示。
17. 作为第三方登录用户，我要在首次登录时补设用户名，以便完成账号初始化。

### B. 用户资料与关系

18. 作为用户，我要编辑自己的头像、昵称和个性签名。
19. 作为用户，我要按用户名或邮箱搜索其他用户，以便添加联系人。
20. 作为用户，我要向他人发送好友请求。
21. 作为用户，我要接受或拒绝收到的好友请求。
22. 作为用户，我要看到所有待处理的好友请求。
23. 作为用户，我要删除好友。
24. 作为用户，我要拉黑某人，使其无法给我发消息、发起通话或发送好友请求。
25. 作为用户，我要查看并管理我的黑名单。
26. 作为用户，我要设置是否允许他人通过用户名/邮箱搜索到我。
27. 作为用户，我要设置谁能给我发消息（所有人 / 仅好友）。
28. 作为用户，我要查看他人的公开资料（头像、昵称、签名、在线状态、最后在线时间）。
29. 作为用户，我要在给拉黑我的人发消息时得到明确失败反馈，而不是消息静默消失。

## Implementation Decisions

### 仓库与模块边界

单一 monorepo，四个顶层工作区：**后端**、**前端**、**桌面壳**、**部署**。

- **后端**为 Rust workspace，按领域拆分 crate：领域核心（用户 / 关系 / 会话 / 消息）、投递（连接、序列、回放、同步）、存储（PostgreSQL 仓储 + 文件存储抽象）、认证与授权、审核、管理接口、实时网关。
- **前端**为单个 Vue 应用，Web / PWA / 管理后台共用构建产物，按路由分包。桌面能力一律经 `desktop-shell` 接口。
- **桌面壳**为两个可互换实现：Tauri（Windows/macOS）与 Electron（Linux），共用同一份前端产物。
- **部署**目录承载 Compose、反向代理配置、备份与监控脚本。

**模块纪律**：后端模块之间只经显式接口通信，禁止跨模块直接读写对方的数据表；前端只经 HTTP/WS 契约与后端通信。这是模块化保证，也是将来替换任何一层的唯一前提。

### 协议契约

- 实时通道为 WebSocket，非实时走 REST。
- WebSocket 信封版本化，承载消息类型、连接级序列、时间戳与负载。
- **契约只有一个真源**：由后端类型生成前端 TypeScript 类型，禁止两端各写一遍；契约漂移必须是编译错误而非运行时故障。
- 三层确认语义必须各自独立且不得混用：传输送达、接收方送达、已读。
- 连接恢复采用"连接级序列 + 会话级序列"双层机制：连接级负责补断线窗口内的事件回放，会话级负责精确补齐消息缺口。检测到缺口时主动重新同步，而不是静默跳过。

### 数据模型要点

- 身份：用户、设备、登录会话（按设备）。
- 关系：联系人、好友请求、黑名单。
- 会话：会话、参与者与角色、每会话的序列计数器。
- 消息：消息主体（全局唯一且时间可排序的标识 + 会话内单调序列号）、编辑历史、表情回应、回执。
- **读状态与同步状态分离**：已读标记按**用户**记录（驱动未读数），同步游标按**设备**记录（驱动补洞）。
- 附件：文件元数据 + 存储引用（经存储抽象层访问，不直接暴露物理路径）。
- 审核：举报、处置记录、敏感词库、审计日志。
- 秘密聊天：只存协议所需的密钥材料引用与不透明密文负载；**明文永不落库、永不索引**。

**关键约束**：

- 消息**不为每个参与者复制**——采用"每会话时间线 + 每用户读游标"模型，这是支撑百万级的核心。
- 会话内序列号必须**原子分配**，它是排序的唯一权威。
- 消息表预留分区键，为将来的水平切分留路。

### 扇出与扩容

- 小群采用写扩散，大群/频道采用读扩散，模型上分开。
- 应用层从第一天**无状态**：连接状态、在线状态、会话状态全部外置。
- 单机阶段使用进程内广播即可；跨节点阶段切换为 Redis 发布/订阅，业务逻辑不变。
- 扩容路线：单机 → 媒体服务独立部署 → 应用层水平扩 → 数据库主从/分区、缓存集群。每一步都不需要改代码逻辑。

### 身份与授权

- 访问令牌 + 刷新令牌，刷新令牌轮换。
- 群内权限判定集中在**一处**（角色 → 能力映射），禁止散落在各处的权限判断。
- 后台角色与普通用户角色完全分离，后台鉴权不走用户端令牌体系。

### 端到端加密模块

- 独立的加密 crate 封装密码学实现，三端复用同一份 Rust 核心：浏览器编译为 WASM，Tauri 直接原生调用，服务端只做密文中继。
- 服务端对秘密聊天**只存路由与不透明负载**，不存明文、不建索引、不参与审核。
- 安全码验证是主动行为：双方需各自比对并标记，标记前 UI 必须显示"未验证"状态。
- 安全码变化必须触发**阻断性告警**，而不是静默接受新密钥。

### 通话模块

- 信令复用主应用的实时连接与鉴权；媒体服务只经 REST 与回调与主应用耦合，主应用不触碰任何媒体端口。
- 一对一通话走点对点，不经服务器媒体转发；群组通话走集中式媒体服务器。两者容量互不占用。
- 中继服务使用**临时凭证**（基于共享密钥的时效性凭证），不接受静态用户名密码。
- **通话是独立窗口**：它是一个独立的路由与独立的 OS 窗口，与主窗口生命周期解耦。这不是样式偏好，是产品硬需求。
- 群组通话的容量上限由单台媒体节点决定（房间不可跨节点拆分），因此人数接近上限时必须显式提示，而不是放任质量恶化。

### 桌面双壳

- 前端组件**不得直接调用任一壳的专有 API**，所有桌面能力经 `desktop-shell` 接口：发起通话、打开通话窗口、屏幕共享选择器、通知与权限、开机自启、更新、托盘。
- Tauri 壳用于 Windows 与 macOS；Electron 壳用于 Linux（因为 Linux 的 WebView 引擎缺失通话所需的 WebRTC 能力）。
- 通话窗口在两个壳中都是独立窗口；Linux 屏幕共享走系统级门户选择器，应用内不做抓源网格。
- 必须有**验证闸门**：在目标发行版上断言 WebRTC 相关全局能力存在。不依赖传闻。

### 前端模块

- 状态按归一化实体管理，避免会话/消息在多处重复存储。
- 乐观发送、离线队列、重连回放是**一等公民**，不是后补的补丁。
- 消息列表虚拟滚动必须支持反向滚动与动态高度。
- 契约类型由后端生成，前端不得手写。
- 动效是验收项：消息进出、列表切换、窗口转场、通话状态变化均需动效，且必须尊重"减少动态效果"偏好。
- 界面语言中文优先，但 i18n 基础设施从第一天就在。

### 管理后台

- 与主应用同仓，独立路由 + 独立鉴权入口。
- 审核范围**只覆盖云端会话**；秘密聊天在任何审核视图中都不可见，且这一点由代码结构保证（而非查询条件约定）。
- 所有管理员操作写审计日志。

## Testing Decisions

**什么算好测试**：只测外部可观察行为，不测实现细节。断言"系统做了什么"，而不是"内部调用了哪个函数"。

**三条接缝**（接缝越少越好，能用高层就不用低层）：

1. **后端主接缝 —— 真实 HTTP/WS API + 真实 PostgreSQL**。每个后端行为都从这里验证：起真实服务、连真实数据库、用真实 WebSocket 客户端跑完整流程（注册 → 登录 → 发消息 → 收消息 → 已读 → 断线重连补洞）。
   **不 mock 数据库**——序列号原子分配、唯一约束、分区行为本身就是被测对象。纯逻辑（缺口检测算术、敏感词匹配、权限判定）走单元测试，因为它们不需要接缝。

2. **前端主接缝 —— 状态层与组件边界**。测状态层的外部行为（归一化缓存、乐观发送、重连回放），不测组件内部实现。网络层在**网络接缝**上拦截（MSW），而不是 mock 具体函数。

3. **契约接缝 —— 一份协议真源**。WS 信封与 REST 契约由后端类型生成前端类型，契约漂移变成编译错误。

**端到端**：只覆盖关键旅程，不追覆盖率。至少覆盖：注册→登录→单聊收发→已读；建群→邀请→收消息；秘密聊天建立→安全码验证→收发；发起通话→接通→挂断。

**密码学**：加密模块用**已知测试向量**验证（跨实现向量），绝不自己发明加密用法，也不自己写密码学原语。

**数据库相关**：迁移脚本可在空库上从头跑通，也必须能在已有数据的库上幂等升级。

**验证闸门**：Linux 桌面端在目标发行版（Ubuntu LTS、Fedora、Arch）上断言通话相关能力存在，并记录引擎版本。这是对"Linux 必须能通话"这条硬需求的持续验证。

## Out of Scope

- **原生移动应用**（Android / iOS 原生壳）。移动端以 PWA 形态覆盖。
- **群组端到端加密**（秘密群聊）。本次 E2EE 只覆盖一对一秘密聊天。
- **Bot / 开放平台 API**。不做第三方机器人与应用市场。
- **联邦 / 跨实例互通**。不做与其他 IM 协议的桥接。
- **增值 AI 能力**（消息翻译、语音转文字、智能回复）。
- **服务端搜索秘密聊天**。加密内容不参与服务端索引，这是端到端加密的必然结果，不是功能缺失。
- **在服务器上编译后端**。构建一律在 CI 或本地完成。

### 已确认的硬约束（不得在实现中妥协）

1. 通话必须在**独立窗口**中，不得做成应用内浮层。
2. Linux 桌面端**必须能通话**，不得降级到浏览器。
3. 界面**必须有动效**，且必须尊重"减少动态效果"。
4. **秘密聊天不参与内容审核**，代码与界面双重保证。
5. **不在服务器上编译 Rust**；构建走 CI，服务器只拉镜像。
6. WebSocket 客户端**必须有重连逻辑**（反向代理重载配置会强制断开连接，这是默认行为）。
7. 契约**只有一个真源**；前端类型由后端生成。
8. 后端测试**不 mock 数据库**。
