# 2 vCPU / 2 GB VPS: Postgres + Redis + Docker ops research

Date: 2026-09-16
Scope: single-box Docker Compose stack (Rust/Axum + PostgreSQL 16 + Redis + Caddy + coturn, later LiveKit).
Target load: hundreds of DAU, tens of concurrent WebSockets. Solo operator.

**Method note**: capacity/tuning numbers come from vendor docs, PostgreSQL docs, and configurator
projects that publish their arithmetic. Blog numbers marked "(blog)" are directional. Third-party
benchmark blogs (johal.in, medium) are treated as *claims*, not measurements - verify on your hardware.

---

## (a) PostgreSQL 16 on a shared 2 GB box

### The central problem with every "2 GB VPS" guide

Configurators assume the box is **dedicated to PostgreSQL**. Evidence: PGConfig's own generated output
for `total_ram=2GB` returns `effective_cache_size = 2GB` - 100% of RAM as a cache hint, which only
makes sense if nothing else lives on the machine.

> `# Generated by PGConfig 3.6.1 (507fdd3)`
> `shared_buffers = 512MB` / `effective_cache_size = 2GB` / `work_mem = 5MB` /
> `maintenance_work_mem = 102MB` / `min_wal_size = 1GB` / `max_wal_size = 4GB` /
> `random_page_cost = 1.1` / `effective_io_concurrency = 200` /
> `max_worker_processes = 8` / `max_parallel_workers = 8` / `max_parallel_workers_per_gather = 2`
> - https://api.pgconfig.org/ (UI: https://pgconfig.org/ , https://pgtune.leopard.in.ua/)

`shared_buffers = 25% of RAM = 512MB` is repeated by a 2 GB-specific walkthrough
(https://rdp.sh/en/blog/postgresql-tuning-for-a-small-vps-a-practical-walkthrough) - but so is the
command in the same article's troubleshooting section: *"Almost always `work_mem` set too high, or too
many connections. Drop `work_mem` to 4 MB, set `max_connections` to 20, and add PgBouncer."*

Conclusion: **512MB is the dedicated-server answer.** Here Postgres must fit inside a cgroup alongside
Redis, the app, Caddy, coturn and a monitor - budget it as a cgroup share, not a fraction of the host.

### Why 25% and not more

- `shared_buffers` is Postgres's own page cache; the OS page cache caches the *same* pages. Pushing it
  to 60-70% double-caches and starves per-backend memory
  (https://chat2db.ai/resources/blog/postgresql-conf-performance-tuning).
- `effective_cache_size` **allocates nothing** - it is a planner hint.
- `work_mem` is **per sort/hash/aggregate node**, not per query and not per connection. One query can
  allocate it many times, hash nodes get `work_mem x hash_mem_multiplier` (2.0 default since PG15), and
  each parallel worker gets its own allowance (https://mydba.dev/blog/postgres-max-connections-memory-guide):
  *"`max_connections x work_mem` is both wrong and useful. Wrong as a prediction, because most
  connections are idle and allocate nothing... Useful as a fear, because a single connection running a
  parallel hash join can consume many multiples of `work_mem` on its own."*
- `max_connections` is **slot allocation, not a throttle** - the postmaster sizes shared-memory arrays
  for the full ceiling at startup whether or not clients connect; "on the order of tens of kilobytes"
  per slot (same source).

### Recommended start for THIS box (shared, cgroup-limited)

```conf
shared_buffers = 384MB          # ~19% of host RAM, ~30% of the container budget (256MB if tight)
effective_cache_size = 1GB      # hint only; RAM left to the box after other containers
work_mem = 4MB                  # small on purpose: multiplied per node/worker
maintenance_work_mem = 64MB     # VACUUM / CREATE INDEX
wal_buffers = -1                # auto
max_connections = 40            # default 100 is a memory problem waiting to happen here
superuser_reserved_connections = 3
idle_in_transaction_session_timeout = '60s'
statement_timeout = '30s'
random_page_cost = 1.1
effective_io_concurrency = 200
maintenance_io_concurrency = 200
checkpoint_completion_target = 0.9
min_wal_size = 256MB
max_wal_size = 1GB              # PGConfig suggests 1GB/4GB; smaller disk here
max_worker_processes = 4
max_parallel_workers = 2
max_parallel_workers_per_gather = 1   # PGConfig says 2; 1 avoids stealing both cores
max_parallel_maintenance_workers = 1
huge_pages = off
wal_compression = on
log_min_duration_statement = 500ms
log_checkpoints = on
log_autovacuum_min_duration = 10s
```

Size the cgroup against the **cgroup limit, not host RAM** - a common failure is OOM inside a container
while the host still shows free memory (mydba.dev, symptom #5).

### Autovacuum: do NOT disable it, do NOT over-staff it

Defaults (https://www.postgresql.org/docs/16/runtime-config-autovacuum.html): `max_workers = 3`,
`vacuum_scale_factor = 0.2`, `cost_limit = 200`, `cost_delay = 2ms`.

- **Each worker consumes its own `maintenance_work_mem`/`autovacuum_work_mem` independently** - raising
  `max_workers` on a 2 GB box multiplies memory
  (https://pgmonitoring.com/blog/postgresql-autovacuum-tuning-guide).
- Raising `max_workers` without raising the shared `cost_limit` gives each worker *less* budget.
- "Disabling autovacuum on any table guarantees eventual wraparound. Never do this."

Verdict for 2 vCPU / 2 GB sharing CPU and I/O with the app:
```conf
autovacuum_max_workers = 2          # 3 acceptable; 5+ is wrong here
autovacuum_vacuum_cost_limit = 200  # deliberately throttled: do not fight foreground queries
autovacuum_vacuum_cost_delay = 2ms
autovacuum_analyze_scale_factor = 0.05
```
Then tune **per table** for high-churn tables (messages, sessions, presence, tokens) - global tightening
vacuums every tiny table more often for no benefit:
```sql
ALTER TABLE messages SET (
  autovacuum_vacuum_scale_factor = 0.02,
  autovacuum_vacuum_threshold = 1000,
  autovacuum_analyze_scale_factor = 0.01
);
```
Before blaming config, check for a long-lived or idle-in-transaction session holding the xmin horizon
(`pg_stat_activity`, `pg_replication_slots`).

### pgBouncer: NOT needed at this scale - and for a Rust app it may be counterproductive

Postgres is **process-per-connection**: each connection is a forked OS process, ~5-10 MB RSS even when
idle, plus its own catalog caches (https://schoolofweb.net/en/posts/postgres-practice-2-connection-pooling/ ,
https://planetscale.com/blog/scaling-postgres-connections-with-pgbouncer). And: *"Once concurrently
active connections exceed a few multiples of the CPU core count, total throughput goes down, not up."*
From mydba.dev: *"I've never seen a web application that needed more than 200. Most teams asking for
500 need PgBouncer with `pool_size = 25`."*

pgBouncer is justified when connection demand is **multiplied across processes/instances**
(https://rivestack.io/blog/postgresql-connection-pooling-pgbouncer):
> "You need PgBouncer if your application has multiple processes or pods each maintaining their own
> connection pool, and the total exceeds PostgreSQL's max_connections." / "If you have fewer than ~50
> concurrent [peak] connections ... you don't."

You have **one Axum process on one box**, and the Rust-specific counter-argument is explicit:
> "Skip pgbouncer. Preparing statements is a significant throughput increase (I've clocked double the
> throughput because of it). Run fatter rust servers, lean on sqlx connection pooling per process,
> skip pgbouncer. ... pgbouncer isn't necessary when a single rust process can handle 30 concurrent
> connections with ease." - https://www.reddit.com/r/rust/comments/1fuwhtb/production_sqlx_and_pgbouncer/

Same thread: sqlx + pgBouncer transaction mode produced `prepared statement "sqlx_s_1" does not exist`
(pgBouncer needs >=1.21 and `max_prepared_statements`; older builds default it to 0).

**Verdict:** use `sqlx::PgPool` directly with `max_connections` **10-20** (start ~cores x 4 = 8-10,
measure). Revisit pgBouncer only if you add a second app instance, a worker fleet, or serverless. If you
do: **transaction mode**, and drop session-state assumptions (no session-level `SET`, no
`LISTEN/NOTIFY`, no session advisory locks - use `SET LOCAL`, `pg_advisory_xact_lock`), and set
`max_prepared_statements`.

## (b) Redis on the same box

### Sizing

- Never run Redis without `maxmemory` - at `maxmemory 0` it grows until the kernel intervenes.
- The generic rule (50-75% of VPS RAM) **does not apply**: Redis is one of seven containers.
- If you enable snapshotting (fork/COW): *"roughly 50-60% of available RAM, leaving room for copy-on-write
  overhead during a fork."* (https://acemq.com/blogs/redis-eviction-policy/)
- Budget **128-192MB**.

### The trap: presence state and cache in one instance

`allkeys-lru` on an instance holding must-keep state is a known production failure:
> "users get logged out at random, a distributed lock is acquired twice, a rate limiter resets ... A
> non-zero `evicted_keys` on an instance that holds state is the tell." (acemq.com)

Decision rule:
- **Everything in Redis is reconstructable** (presence TTLs, caches, socket registry) -> `allkeys-lru`
  + a TTL on every key. This is the right model for chat: presence = `SET presence:<user> <node> EX 60`
  refreshed on heartbeat, so a crashed node's ghost presence self-cleans.
- **Something must never be evicted** (refresh tokens, session records) -> give those keys no TTL and
  use `volatile-lru` (volatile policies only evict keys that have a TTL), or better run a second small
  instance with `noeviction`. `maxmemory` is instance-wide, not per-DB - separate logical DBs do **not**
  isolate eviction. Only separate processes do.

### Persistence: off is right for presence/cache

https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/
```conf
save ""
appendonly no
```
> "With persistence disabled, all data is lost on restart. Applications must handle a cold Redis cache."
> Disabling it also eliminates disk I/O, fork latency spikes and COW memory overhead.

Design around it: a Redis restart = total state loss; clients reconnect and re-register presence. Any
auth/session *not* in Postgres must be JWT or DB-backed, never Redis-only. Pub/Sub has **no persistence and
at-most-once delivery by design** - an offline subscriber misses the message for good, and a subscriber
needs a dedicated subscribe-only connection (https://redis.io/docs/latest/develop/use-cases/pub-sub/).
Do not use Pub/Sub as a durable queue; if you need replay, use Streams (and then reconsider persistence).

### Recommended config

```conf
bind 0.0.0.0                      # container network only; never publish 6379 to the host
protected-mode yes
requirepass <LONG_RANDOM>
maxmemory 160mb
maxmemory-policy allkeys-lru
maxmemory-samples 10              # better eviction quality than default 5, still cheap
save ""
appendonly no
# If you DO need durability, prefer AOF for presence-like data:
# appendonly yes
# appendfsync everysec            # worst case ~1s of writes lost
tcp-keepalive 60
timeout 300                       # reap dead subscriber connections
```
Checks: `INFO memory` (`used_memory` vs `maxmemory`, `mem_fragmentation_ratio`), `INFO stats`
(`evicted_keys`, `keyspace_hits/misses`). Non-zero `evicted_keys` on state you care about is a bug.

## (c) Docker + Compose overhead, limits, swap, OOM order

### What Docker itself costs

- `dockerd` + `containerd` together sit near **~100 MB** RSS
  (https://www.ssdnodes.com/learn/docker-on-a-vps).
- A container is a process in a cgroup, not a VM: no guest kernel, no fixed allocation. "That is why a
  full stack fits in 2 GB when the same stack built from virtual machines would not."

### Host reserve / container budget

ssdnodes' budget model: **`host_reserve_mb = 768 MB` on a 2 GB box** for OS, daemon and headroom;
**1280 MB is the container budget**. Explicit warning: *"`docker compose build` and `pg_dump` both want
memory at the worst moment"* - leave the top of the budget unspent.

### Limits do two different jobs

| Mechanism | Effect |
|---|---|
| `memory` / `deploy.resources.limits.memory` | hard ceiling; exceeding it = **cgroup OOM, kill inside the container only** (`OOMKilled: true`, exit **137**) |
| `memory-reservation` / `reservations.memory` | soft limit used under host contention |
| `memswap_limit` / `--memory-swap` | total memory+swap; set **equal to memory** to disallow container swap |
| `oom_score_adj` | who dies first on a **global** (host-wide) OOM |

Key facts:
- **Without a limit, the kernel picks a victim by size across the whole machine - and it is often your
  database while the leaking container keeps running** (`Out of memory: Killed process ... (postgres)`,
  no `Memory cgroup` prefix in the log). "That is why a limit on every service matters more than the
  exact value of any single limit." (https://www.ssdnodes.com/learn/docker-on-a-vps)
- A container with `--memory=512M` and **no** `--memory-swap` gets **unlimited swap** by default.
  *"Always set `--memory-swap` equal to `--memory` to disable swap for critical services. You want OOM
  kill, not swap death."* (https://blog.gntech.me/posts/2026-05-13-docker-container-resource-limits/)
- `deploy.resources.limits` **is honoured by plain `docker compose up`** (no Swarm needed); only other
  `deploy` keys (`replicas`, `placement`) are ignored. Minimum memory limit is `6m`.
  (https://jacar.es/en/docker-resource-limits-and-logging/)
- cgroup v2 nuance: `--oom-kill-disable` no longer kills - it **pauses** the container (tasks in D
  state), which is worse than an OOM kill. Docker's docs also advise against extreme negative
  `oom_score_adj` or `oom-kill-disable`
  (https://docs.docker.com/engine/containers/resource_constraints/).

### OOM protection order (host/systemd side)

Starting values (https://fdcservers.net/blog/linux-oom-killer-tuning-for-vps-a-practical-guide):
- `sshd`: `-1000` - losing remote access during a memory crisis is the worst outcome.
- PostgreSQL, Redis: `-800` to `-900` - strong protection, not immunity.
- App workers, batch jobs, cron, monitors: `+100` to `+500` - kill these first.
- **Do not set everything to -1000** - "if nothing is killable, the kernel will eventually panic or
  freeze instead."

Containers are not systemd units, so rely primarily on per-container `memory` limits to localise the
failure, and use `oom_score_adj` where supported. Watch PSI (`/proc/pressure/memory`) and `MemAvailable`
(keep above ~10-15% of `MemTotal` at peak) rather than waiting for `dmesg`.

### Swap / zram - the honest answer for *this* box

Most cloud images ship with **no swap** (`swapon --show` prints nothing).
(https://www.ssdnodes.com/learn/does-your-vps-need-swap)

- **Add a swap file: yes, 1 GB.** The old "2x RAM" rule comes from hibernation, which a VPS never does.
  It is an *alarm buffer*, not extra RAM - it buys minutes to notice and fix.
- `vm.swappiness = 10` (not the desktop default 60). **`0` does not disable swap** - it postpones reclaim
  until near-OOM and pushes the OOM killer *forward*.
- **zram: skip on this box.** zram trades CPU for memory. *"Use zram when you have CPU headroom and
  little spare disk, and a swap file when the opposite is true ... On a VPS with a small CPU allowance,
  that cost lands on the resource you are already short of."* This box has 2 vCPU and runs a database.
  If sustained pressure appears later, add a *small* zram device (25% of RAM) with higher priority than
  the swap file - do not enable both blindly.
- Docker: give `postgres` and `redis` **no container swap** (`memswap_limit == mem_limit`).
  *"Database-heavy VPS: buy RAM before you buy swap. Swapping database pages destroys latency."*
- Check your provider: AWS charges per EBS I/O and advises against swap; local-NVMe providers
  (DigitalOcean/Linode/Vultr/Contabo/Hostinger) are fine. Confirm what your HK VPS uses.

### Compose/ops hygiene that bites on small boxes

- **Build images elsewhere.** *"Building images on a box that size will fail or kill something else, so
  build elsewhere and pull the finished image."* Build in CI or locally, push to a registry, pull here.
- `restart: unless-stopped` on every service - containers do **not** come back after a reboot otherwise.
- Docker writes its own iptables rules: **a published port bypasses UFW**. Bind admin ports to
  `127.0.0.1` and let Caddy proxy them.
- `docker system df` + `df -h /` monthly; prune exited containers (they retain logs until removed).
- Consider a non-default Docker data-root if the root disk is small.

## (d) Capacity: WebSockets, connections, Postgres math

### Memory per WebSocket connection

Vendor-scale numbers for Rust/Axum are **kilobytes**, not megabytes - but the spread is real and blog
figures are mixed quality. Use a range, not a promise:

| Source | Figure | Notes |
|---|---|---|
| normogen perf notes (2026-02) | Axum **~1.5 KB/conn**, Actix ~2 KB; base RSS 12 MB | framework/task overhead only |
| Medium (Axum vs Actix vs Express) | Axum **4.2 KB/conn** (Actix 4.8) | +-15% variance claimed |
| johal.in (tokio-tungstenite 0.23, blog) | **7.4 KB idle/conn**, 12.8 KB in 0.21 | claims 1 KB aligned frame buffers |
| rexai / Ark Protocol benchmark (blog) | Rust+Axum **~52 KB/conn** WS (SSE ~31 KB) | includes frame buffers + per-conn state at 100k conns |

**Planning figure: 20-64 KB per idle WebSocket.** At 50-100 concurrent connections that is **1-6 MB
total**. Memory is emphatically not your constraint.

The other component is **kernel socket memory**, which the app does not control:
> "If they are literally idle, the only resource that sockets really consume is kernel memory."
> - https://users.rust-lang.org/t/ballpark-number-of-mostly-idle-tcp-connections-that-async-server-can-handle/92910

### What actually limits you on 2 vCPU

1. **File descriptors.** `ulimit -n` / `LimitNOFILE` (systemd drop-in for the Docker daemon *and* per
   container). This is the first wall, not RAM.
2. **CPU when the message rate rises.** Idle connections are nearly free; fan-out and JSON encode/decode
   are not.
3. **`net.core.somaxconn` / accept backlog** during reconnect storms.
4. **Application-level `tokio::sync::mpsc` channels** - use **bounded** channels (16-32) plus a registry;
   unbounded per-connection channels are the standard way to OOM a chat server under backpressure.
5. **Zombie connections.** Without ping/pong, dead connections accumulate. Implement heartbeats (Axum's
   WebSocket extractor auto-handles pong frames; you must send the pings).

### Allocator RSS is not a leak

A recurring Axum-relevant gotcha: RSS grows under load and does not return to baseline because
allocators retain freed memory. Usually not a leak. Measure `allocated` vs `resident` before chasing it.
jemalloc returns cached pages only after a delay and not at all when fully idle; the fix is
`background_thread:true,tcache_max:4096`
(https://github.com/tokio-rs/tokio/issues/7064 , https://github.com/jemalloc/jemalloc/blob/dev/TUNING.md).
Consequences: (i) do not size the memory limit from a post-load-test RSS, (ii) set a container limit so
growth cannot eat the host, (iii) use mimalloc or jemalloc with a background thread if it matters.

### Postgres connection math - why NOT one PG connection per WebSocket

The most important architectural rule here; canonical write-up:
> "Each connection is a `postgres` backend process. It consumes approximately 5-10 MB of memory. It
> occupies a slot in `max_connections` ... An idle connection that is doing no work costs nearly as much
> as an active one." / "With HTTP, a request handler's thread lives for 50-500ms ... With WebSocket
> consumers, there is no churn. Connections accumulate. 200 concurrent WebSockets means 200 threads,
> means 200 database connections held indefinitely. PostgreSQL's default `max_connections` is 100."
> - https://goldlapel.com/grounds/connection-pooling/django-channels-postgres-connection-exhaustion

Arithmetic for 200 concurrent sockets:
- **One PG conn per socket**: 200 backends x ~7 MB = **~1.4 GB RSS** and 200 slots > `max_connections`
  -> `FATAL: sorry, too many clients already`. Catastrophic on 2 GB.
- **One sqlx pool, `max_connections = 15`**: 15 backends x ~7 MB = **~105 MB**, and the 16th concurrent
  query waits in a fair queue instead of failing: *"by using a single connection pool for your whole
  application, you can ensure that you don't exceed the connection limit of your database server while
  allowing response time to degrade gracefully at high load"*
  (https://docs.rs/sqlx/latest/sqlx/struct.Pool.html).

Rules:
- `pool_max` ~= 2-4 x CPU cores, **measured**. Here: **8-15**, not 40.
- DB work lives in the event path, never held for the socket's lifetime - query, release.
- Keep minimal per-connection state in memory (`user_id`, `device_id`, subscriptions); authoritative
  state in Postgres/Redis. *"Each WebSocket connection in uWS costs ~1.3 KB for the socket itself ... be
  careful about what you attach to each socket."*
- Reconnect storms are a write-amplification hazard: 200 reconnects in 2 s each triggering
  state-hydration reads (or worse, writes) saturate the pool. Debounce 500-1000 ms and keep
  presence/last-seen in Redis, not Postgres
  (https://webline.global/posts/why-your-websocket-reconnects-trigger-cascading-database-write-floods/).

### Caddy-specific: reloading config drops your WebSockets

> "By default, WebSocket connections are forcibly closed (with a Close control message sent to both the
> client and upstream) when the config is reloaded. Each request holds a reference to the config, so
> closing old connections is necessary to keep memory usage in check. This closing behaviour can be
> customized with the `stream_timeout` and `stream_close_delay` options."
> - https://caddyserver.com/docs/caddyfile/directives/reverse_proxy

Consequences: a `caddy reload` (any cert/route change) disconnects every live chat client. Your client
must auto-reconnect with backoff, and deploys cause a reconnect wave. `reverse_proxy` also buffers
responses by default; `flush_interval -1` selects low-latency streaming for SSE/event endpoints.

### coturn

- "Minimum: 0.25 vCPU / 128 MB. Recommended: 1 vCPU / 512 MB. Resource usage scales linearly with the
  number of concurrent active relay sessions." Idle ~64-128 MB; 100-500 sessions ~512 MB.
- Bandwidth is the real cost, not RAM: ~100 Kbps per audio client; ~2 Mbps in+out per peer for WebRTC
  video; a 2 CPU / 4 GB / 250 Mbit box "worked well with a mix of UDP, TCP, and TLS clients. The network
  would always get saturated before the CPU or memory usage became a problem."
  (https://github.com/coturn/coturn/issues/328)
- On a 100 Mbps VPS: roughly **50 concurrent video relay pairs**, or hundreds of audio-only. Budget
  ~192-256 MB. Do not run a big TURN workload on the same 100 Mbps you serve the app from.
- The Debian/Ubuntu package needs `TURNSERVER_ENABLED=1` in `/etc/default/coturn` or it silently does
  nothing.

### LiveKit later (plan the exit before you need it)

- Official sizing is per-project guidance, not one number: a widely repeated figure is **~200 concurrent
  users on a 4 vCPU / 16 GB node** for audio-heavy/small-group video; "2 vCPU / 2-4 GB for
  testing/small deployments" with a caveat to **scale up CPU** for more participants
  (https://www.ramnode.com/guides/livekit , https://celloip.com/blog/self-hosted-livekit-deployment-guide/).
- **2 vCPU / 2 GB is not a group-video box.** "a room with 10+ video participants consumes
  disproportionately more SFU resources than the same room count with audio only."
- LiveKit single-node has no external deps; **multi-node requires Redis** (which you will have)
  (https://docs.livekit.io/reference/internals/livekit-sfu/).
- Ports to plan now: TCP 7880 (signalling), TCP 7881 (ICE/TCP), **UDP 50000-60000** (media, two ports
  per participant), plus TURN 3478/5349. LiveKit has an embedded TURN server.
- Sequencing: ship coturn + 1:1 WebRTC first; move group calls to a second, larger instance rather than
  squeezing LiveKit into this 2 GB box.

## (e) Monitoring that fits the budget

**Prometheus + node_exporter + Grafana = 3 services and 3 listening ports before you have written a
single alert rule**, and *"a metrics server that dies with the box it monitors cannot tell you why the
box died"* (https://www.ssdnodes.com/learn/lightweight-server-monitoring-tools). For one box, skip it.

The 2026 small-VPS consensus is **Beszel + Uptime Kuma**, with Glances for ad-hoc SSH debugging:

| Tool | Agent RAM (idle) | Verdict |
|---|---|---|
| **Beszel** (MIT, hub+agent) | agent ~10-30 MB; hub ~30-50 MB | CPU/RAM/disk/network/temp, **per-Docker-container stats**, S.M.A.R.T., threshold alerts + webhooks, SQLite, optional S3 backups. The default choice. |
| **Uptime Kuma** (MIT) | 60-100 MB with SQLite | Service uptime + status page + **push/heartbeat monitors** + 90+ notification channels. |
| **Glances** | 50-150 MB (Python) | Live terminal view with per-process detail. Use over SSH, not as a service. |
| **Netdata** | **150-400 MB RSS, ~1.2 GB disk/day** at defaults | Excellent depth, wrong tool for a 2 GB box. |

Real Uptime Kuma traps (widely missed):
- **Do not use the embedded MariaDB.** The full Docker image bundles a MariaDB server, and "Embedded
  MariaDB" looks like the easy default in first-run setup. A user hit OOM on a **2 GB** box with ~**50
  lightweight HTTP monitors**; the maintainer's verdict: *"That should be the biggest contributor.
  MariaDB does a few tradeoffs which come at the cost of memory usage. You want sqlite or externalize
  MariaDB where you have the memory for it."* Meanwhile ~250 monitors on **SQLite** averaged **under
  400 MiB**. Use the **`-slim`** image (172 MB vs 573 MB - no Chromium, no MariaDB) and SQLite.
  (https://selfhostpicks.com/uptime-kuma-hardware-requirements/)
- **Do not use browser monitors** (Chromium): known leak; ~800 MB reported with 19 monitors of which 2
  were Chromium (https://github.com/louislam/uptime-kuma/issues/3788). If you need them, use a remote browser.
- Open memory-leak reports exist on 2.4.0 (growing to 3 GB,
  https://github.com/louislam/uptime-kuma/issues/7537). Mitigate with a container `memory` limit so a
  leak restarts the container rather than the box, and keep monitor count/interval sane (20 s intervals
  are 3x the work of 60 s).

**Recommended stack for this box (~120-160 MB total):**
1. **Beszel agent** on the VPS (+ hub, here or on a cheaper/second machine) -> resource history and
   per-container memory; alert on memory/disk/load thresholds.
2. **Uptime Kuma** (`-slim`, SQLite) -> HTTP keyword check on your public endpoint, TCP 443, DNS, SSH
   reachability, **and push monitors for the nightly backup job** (silence = missed backup).
3. **External check** for "is the VPS alive at all". A monitor on the box cannot tell you the box is
   down. At minimum add a free third-party uptime check (or a cron on another machine) hitting your
   public URL, alerting on failures and TLS expiry.
4. `htop`/`btop`/`Glances` for the interactive case.

Alert discipline (multiple sources converge): start with **two** alerts - **disk above 85%** and **the
one service you care about no longer running** - delivered to a channel you actually read (Telegram,
Discord, ntfy). Alert fatigue is how monitoring dies.

Also alert on: container restarts (`restart: unless-stopped` hides OOM loops), Postgres connection
utilisation percent, Redis `evicted_keys` on state you care about, non-zero swap-in/out (`si`/`so` in
`vmstat`) sustained, and `MemAvailable` below ~10-15%.

## (f) Backups: pg_dump + rclone to object storage

### Shape of the strategy

| Layer | Target | Retention | Why |
|---|---|---|---|
| Postgres logical dump | `pg_dump -Fc` -> gzip -> **encrypt** -> object storage | local 7d, cloud 30d | custom format restores faster with `pg_restore` |
| Uploaded files / media | `tar`/`restic` -> same bucket, separate prefix | cloud 30-90d | *"A database dump alone isn't enough. File storage deserves the same protection."* |
| Config / compose / `.env` template / Caddyfile | tar -> same bucket | 10 versions | rebuild the box without archaeology |
| Restore drill | onto a different machine | **monthly** | an untested backup is a hypothesis |

RPO with daily dumps = up to 24 h. If that is unacceptable, enable WAL archiving (`archive_command` with
rclone) for PITR - but that is a second, more fragile pipeline. Start with daily dumps and a *tested*
restore.

### Gotchas that cost people hours (from real write-ups)

1. **Use a full connection string / force TCP.** *"Without specifying a host, `pg_dump` uses Unix sockets,
   which often trigger peer authentication. The fix was simply switching to the full connection string."*
   Critical under cron, which runs as a different user.
   (https://asrulkadir.medium.com/beyond-pg-dump-building-a-production-ready-backup-strategy-with-postgresql-rclone-cloudflare-7feafe1856e4)
2. **Use `rclone copy`, not `rclone sync`,** when local and cloud retention differ - `sync` would delete
   your 30-day cloud backups the moment local 7-day files are pruned. Either copy + `rclone delete
   --min-age`, or `sync` + bucket lifecycle rules.
3. **Encrypt before upload, not "server-side".** Either `gpg -c` symmetric with a passphrase file, or
   **`rclone crypt`** - a remote wrapping the S3 remote that encrypts *contents, filenames and folder
   names* before anything leaves the machine (https://rclone.org/crypt/).
4. **Heartbeat the job.** Add an Uptime Kuma push monitor; if the backup never runs, the missing heartbeat
   alerts you. Otherwise you find out during a restore.
5. **`pg_dump -Fc` + stream** - do not write a giant uncompressed temp on a small disk.
6. **Storage choice**: Cloudflare R2 is S3-compatible, has lifecycle rules (retention becomes the
   provider's job) and no egress fees - a good fit for a HK VPS and a solo dev.
7. Verify with `rclone ls` before trusting the remote at all.

### Script sketch

```bash
#!/usr/bin/env bash
# /usr/local/bin/pg-backup.sh
set -euo pipefail

BACKUP_DIR=/var/backups/pg
RCLONE_REMOTE="r2crypt:app-backups/postgres"   # crypt-wrapped S3/R2 remote
RETENTION_DAYS=7
HEARTBEAT_URL="${UPTIME_KUMA_PUSH_URL:-}"
STAMP=$(date -u +%Y-%m-%dT%H-%M-%S)
FILE="$BACKUP_DIR/app_$STAMP.dump.gz.gpg"

log()  { printf '%s %s\n' "$(date -u +%FT%TZ)" "$*"; }
fail() { log "ERROR: $*"; [ -n "$HEARTBEAT_URL" ] && curl -fsS --max-time 10 "${HEARTBEAT_URL}?status=down" || true; exit 1; }

mkdir -p "$BACKUP_DIR"

# 1. Dump. Full connection string forces TCP auth (no peer-auth surprise under cron).
#    -Fc = custom format -> pg_restore, parallel restore, selective restore.
#    Pipe end-to-end: no uncompressed temp file on a small disk.
log "dumping..."
docker compose -f /opt/app/docker-compose.yml exec -T postgres \
    pg_dump -Fc --no-owner --no-privileges "$DATABASE_URL" \
  | gzip -6 \
  | gpg --batch --yes --passphrase-file /root/.backup_gpg_pass -c \
  > "$FILE" || fail "pg_dump failed"

# 2. Sanity: refuse to upload a suspiciously tiny dump.
[ "$(stat -c%s "$FILE")" -gt 10240 ] || fail "dump too small: $(stat -c%s "$FILE") bytes"

# 3. Upload. `copy` (not `sync`) so cloud retention stays independent of local retention.
log "uploading $FILE"
rclone copy "$FILE" "$RCLONE_REMOTE/" --transfers=2 --checkers=4 --retries 3 \
    || fail "rclone copy failed"

# 4. Local retention only (7 days). Cloud retention = bucket lifecycle rule (30d),
#    or: rclone delete --min-age 30d "$RCLONE_REMOTE"
find "$BACKUP_DIR" -name 'app_*.dump.gz.gpg' -mtime +$RETENTION_DAYS -delete

log "OK $(basename "$FILE")"
[ -n "$HEARTBEAT_URL" ] && curl -fsS --max-time 10 "$HEARTBEAT_URL?status=up" || true
```

Cron (UTC; remember HK is UTC+8):
```cron
30 18 * * * /usr/local/bin/pg-backup.sh >> /var/log/pg-backup.log 2>&1
```
Weekly, also push config + file storage to a separate prefix.

### Disaster recovery runbook (must exist before you need it)

1. Provision a new VPS; install Docker + rclone.
2. Restore `rclone.conf` and the GPG passphrase from your password manager - **verify these are stored
   outside the VPS.**
3. `rclone copy` the latest dump + config bundle down.
4. Recreate `.env`, compose files and Caddyfile from the config bundle; restore the Caddy data volume (or
   just re-issue certs).
5. `docker compose up -d postgres`, wait for healthy, then
   `pg_restore --clean --if-exists -d "$DATABASE_URL" < dump`.
6. Restore file storage into its volume.
7. `docker compose up -d`; verify a login + a WebSocket connect + a DB write.
8. **Practise this quarterly on a throwaway box.** The drill is the deliverable.

## (g) Log management: the essentials

Docker's default `json-file` driver **performs no rotation**, and files are plain append-only files under
`/var/lib/docker/containers/<id>/<id>-json.log`. One chatty container can consume tens of gigabytes; the
failure mode cascades - writes slow, daemon latency spikes, image pulls and container creates fail, and
`dockerd` can hang while containers keep running.
(https://www.netdata.cloud/guides/docker/docker-log-rotation/ ,
https://docs.docker.com/engine/logging/drivers/json-file/)

**Daemon default** (`/etc/docker/daemon.json`) - string values are mandatory, and it only applies to
containers created *after* the restart:

```json
{
  "log-driver": "local",
  "log-opts": { "max-size": "20m", "max-file": "5" }
}
```
Then `sudo systemctl restart docker` **and recreate containers**:
`docker compose up -d --force-recreate`.

- **Prefer the `local` driver**: rotates by default (20 MB x 5), compresses rotated files, more efficient
  binary format; `docker logs` still works. Docker's own docs recommend it over `json-file` for exactly
  the disk-exhaustion reason.
- Use `json-file` if you need machine-parsable JSON on disk; then set `max-size` / `max-file` explicitly
  (e.g. `10m` x `3`), also settable per service under `logging: options:` in Compose, plus
  `compress: "true"` (Docker 20.10+). In Compose `logging.options` must be a map; any per-container
  `--log-opt` overrides the daemon default, so a container with its own logging block and no `max-size`
  is unprotected.
- **Exited containers retain their logs** until removed - regular pruning is part of log hygiene.
- **Monitor it**: alert at **70%** of the `/var/lib/docker` filesystem, not 95% ("waiting until 95%
  leaves no room for cleanup"). `docker system df` and `du -sh /var/lib/docker/containers/*/` tell the truth.
- Reduce application log **volume** (level, no request-body logging) before tuning rotation sizes - a
  small `max-size` with a chatty app just rotates more often and loses history exactly when you need it.
- Caddy keeps its own access log: set `roll_size`/`roll_keep` (and disable access logs for health-check
  paths) rather than letting it grow inside the container.

## Resource budget (2 GB / 2 vCPU)

Host reserve (kernel, systemd, journald, sshd, dockerd+containerd) - **768 MB**
Container budget - **1280 MB**

| Service | Typical RSS | Container limit | Notes |
|---|---|---|---|
| postgres:16 | 450-550 MB | `768M` | `shared_buffers=384MB`; `memswap_limit` = `768M` (no swap); most OOM-protected |
| redis:7 | 20-140 MB | `192M` | `maxmemory 160mb`; no persistence; no container swap |
| app (axum) | 20-80 MB | `320M` | allocator RSS drifts up under load - the limit is the safety net, not a leak fix |
| caddy | 15-35 MB | `96M` | |
| coturn | 64-130 MB | `192M` | scales with relay sessions; bandwidth is the real cost |
| beszel agent | 10-25 MB | `64M` | |
| uptime-kuma (`-slim`, SQLite) | 60-100 MB | `192M` | limit it: open leak reports |
| **typical total** | **~640-1060 MB** | **~1.8 GB** | limits sum above the 1280 MB budget *by design* - limits cap blast radius; the **typical** column is what must fit |

Host-level: 1 GB swap file, `vm.swappiness=10`, no zram initially. Headroom stays unspent for
`docker compose build` and `pg_dump`. Build images off-box.
